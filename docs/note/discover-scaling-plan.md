# 탐색 성능 확장 계획

> 작성일: 2026-11-10 · 관련 브랜치: `perf/db-query`

## 현재 상태 (적용 완료)

- **키워드별 보유자 상한**: 비슷한 키워드마다 최근 활동(`user_keyword.updated_at`) 순으로 최대 500명만 후보로 읽는다.
  - 키워드 하나에 500명이 몰리기 전까지는 결과가 이전과 동일하다.
  - 인덱스 `idx_user_keyword_active_combo`를 `(keyword_id, updated_at DESC, user_id) WHERE is_active`로 교체 (V13).
- **탐색 요청 로그**: `LogAction.DISCOVER_REQUEST` (target, seed, firstPage, resultCount)
  - 조회자(viewer)는 남기지 않는다. target과 함께 남으면 열람 이력이 되고 분석에도 필요 없다.

측정 기준 (PG17, Supabase Nano 사양 재현: 메모리 512MB · CPU 0.5, 사용자 20만 · 키워드 3만):

| | 이전 | 상한 적용 후 |
|---|---|---|
| 인기 키워드 사용자 | 건당 69ms (초당 14건) | 건당 28ms (초당 35건) |
| 무작위 사용자 | 건당 42ms (초당 24건) | 건당 21ms (초당 46건) |

## 다음 단계

### 1. 로그로 결과 캐시 효과 판단 (출시 후 몇 주)

`DISCOVER_REQUEST` 로그에서 아래 두 비율을 계산한다.

- **같은 대상 재요청 비율**: 같은 `target`이 5분 안에 다시 요청된 비율 → 대상별 캐시 적중률
- **페이지 넘김 비율**: 같은 `seed`(탐색 세션)로 이어진 요청 수 → 세션 내 재계산 절약분

### 2. 비율에 따라 결정

- **높음** → 대상 사용자(`targetUserId`) 기준 결과 캐시 도입
  - 서버 메모리 캐시(예: Caffeine)로 시작, TTL 수 분
  - 캐시 대상: 후보 풀(셔플 전). viewer 제외 · 셔플 · 페이지 분할은 서버에서 처리
  - 감수할 점: 새 게시물이 몇 분 늦게 탐색에 반영됨
- **낮음** → 캐시 대신 DB 플랜 업그레이드로 대응

### 3. DB 플랜 업그레이드

- 데이터가 프리티어 용량(500MB)에 가까워지면 어차피 필요
- Supabase 문서상 Medium 이하는 공유 CPU라 플랜만으로 CPU가 크게 늘지 않으므로, 쿼리 비용 관리(상한 · 캐시)를 병행한다

### 4. 부하 테스트

- 캐시 · 업그레이드 후 운영과 같은 구성으로 동시 사용자 수를 늘려가며 한계 확인

## 참고

- Nano 기준 커넥션 풀 5개, 커넥션 획득 타임아웃 3초: 처리량을 넘는 순간 요청은 3초 뒤 실패한다.
- 비슷한 키워드 검색(HNSW)은 PG17에서 `ORDER BY 거리, id`로도 인덱스를 탄다(Incremental Sort). PG16에서는 못 탄다 → Postgres 버전 변경 시 재확인.
- 결과 수가 적은 초기 상황(임계값 0.5를 넘는 사용자가 적음)은 상한과 무관하다. 필요하면 임계값 완화 등 별도 보완책을 검토한다.
